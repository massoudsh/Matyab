# موتور هوش مصنوعی: کیفیت، قیمت، مچینگ

این سه سرویس، مزیت رقابتی اصلی متریاب نسبت به آگهی‌نامه‌ی عمومی هستند.

## ۱. Quality Scoring
**ورودی:** عکس(های) مصالح + توضیحات متنی فروشنده + دسته‌ی مصالح.
**خروجی:** نمره‌ی کیفیت (۰-۱۰۰)، رده (A/B/C)، فهرست مشکلات احتمالی (مثلاً «زنگ‌زدگی مشاهده‌شده در میلگرد»).

**رویکرد فاز MVP:** ارزیابی دستی توسط خودِ کاربر + بازبینی ادمین (بدون مدل AI واقعی، برای اعتبارسنجی سریع).
**رویکرد فاز V1:** مدل تحلیل تصویر (vision) اختصاصی هر دسته‌ی مصالح + قوانین دامنه (مثلاً برای بلوک: ترک‌خوردگی؛ برای میلگرد: خوردگی/زنگ‌زدگی؛ برای کاشی: لب‌پریدگی).

## ۲. Price Suggestion
**ورودی:** دسته‌ی مصالح، نمره‌ی کیفیت، منطقه/شهر، تاریخچه‌ی قیمت مشابه (جدول `PriceHistory`).
**خروجی:** قیمت پیشنهادی + بازه‌ی اطمینان (min/max) + دلیل کوتاه («بر اساس ۱۲ معامله‌ی مشابه در تهران طی ۳۰ روز اخیر»).

**نکته‌ی مهم:** این سرویس هرگز قیمت را «قطعی» اعلام نمی‌کند — همیشه به‌عنوان پیشنهاد قابل‌مذاکره نمایش داده می‌شود تا اعتماد فروشنده حفظ شود.

## ۳. Matching Engine
**ورودی:** یک Listing جدید یا یک Request جدید.
**منطق تطابق:**
1. تطابق دسته‌ی مصالح (اجباری).
2. هم‌پوشانی مقدار (Listing.quantity در بازه‌ی قابل‌قبول Request.quantity).
3. فاصله‌ی جغرافیایی → هزینه‌ی حمل تخمینی → آیا با احتساب حمل هنوز به‌صرفه است؟
4. تطابق کیفیت با نیاز اعلام‌شده (مثلاً پروژه‌ی سازه‌ای رده A می‌خواهد، پروژه‌ی محوطه‌سازی رده B کافی است).
5. (فاز V1) شباهت معنایی توضیحات با embedding در `pgvector` برای موارد نامنظم/غیراستاندارد.

**خروجی برای کاربر:** یک کارت پیشنهاد با متن توضیح‌پذیر، نه فقط یک عدد:
- «این گزینه به‌صرفه است» (قیمت + حمل کمتر از خرید نو)
- «این یکی ریسک کیفیت دارد» (نمره‌ی کیفیت پایین یا رده نامناسب)
- «این خرید با حمل دیگر ارزان نیست» (فاصله زیاد، هزینه‌ی حمل قیمت را جبران‌ناپذیر می‌کند)

## معماری اجرا
- Quality Scoring و embedding سنگین → صف async (Redis + worker) تا API سریع بماند.
- Price Suggestion و Matching rule-based فاز MVP → همگام (synchronous) و سبک.
- در فاز V2 امکان جدا شدن این سه سرویس به microservice مستقل (در صورت رشد بار).
