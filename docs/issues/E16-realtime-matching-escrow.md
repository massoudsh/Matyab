# Epic 16 — موتور matching real-time و پرداخت امن (Escrow)
لیبل: `epic`, `v2`, `backend`, `ai`, `db`

مسئله (روادمپ فاز ۳): مچینگ فعلی rule-based و synchronous است (فقط هنگام ثبت Request). برای مقیاس V2،
نیاز به مچینگ real-time (وقتی Listing جدید هم ثبت می‌شود، بلافاصله Requestهای منتظر را چک کند) و یک لایه‌ی
پرداخت امن بین خریدار و فروشنده داریم (فعلاً معامله کاملاً بیرون از پلتفرم انجام می‌شود).

---
### ISSUE-1601: trigger مچینگ روی Listing جدید (تکمیل ISSUE-502)
**شرح:** علاوه بر trigger فعلی روی Request جدید، وقتی Listing جدید تأیید می‌شود (`ACTIVE`)، Requestهای فعال هم‌دسته چک شوند.
**معیار پذیرش:**
- [ ] `listings.service.ts` هنگام تغییر وضعیت به `ACTIVE` تابع معکوس مچینگ را صدا بزند
- [ ] جلوگیری از ساخت match تکراری برای یک جفت (listingId, requestId)

---
### ISSUE-1602: صف پردازش async مچینگ
**شرح:** با رشد حجم آگهی/درخواست، مچینگ synchronous کند می‌شود؛ صف (Redis/BullMQ) برای پردازش پس‌زمینه.
**معیار پذیرش:**
- [ ] مچینگ از request-response خارج و به job تبدیل شود؛ نتیجه از طریق Notification (E14) به کاربر می‌رسد

---
### ISSUE-1603: مچینگ معنایی با pgvector
**شرح:** جایگزینی/تکمیل مچینگ دسته‌ای با embedding توضیحات و عکس مصالح (زیرساخت pgvector از ابتدا در `db/schema.sql` هست ولی استفاده نشده).
**معیار پذیرش:**
- [ ] ستون embedding روی Listing/MaterialRequest
- [ ] امتیاز نهایی ترکیب امتیاز rule-based فعلی + شباهت embedding

---
### ISSUE-1604: مدل داده‌ی Escrow
**شرح:** به‌جای نمایش مستقیم شماره تماس بعد از پذیرش، پرداخت از طریق پلتفرم نگه‌داری شود تا معامله نهایی تأیید شود.
**معیار پذیرش:**
- [ ] فیلدها روی `Transaction`: وضعیت escrow (`HELD`/`RELEASED`/`REFUNDED`)، درگاه پرداخت، شناسه‌ی تراکنش درگاه

---
### ISSUE-1605: اتصال درگاه پرداخت ایرانی
**معیار پذیرش:**
- [ ] `POST /transactions/:id/pay` → ایجاد لینک پرداخت
- [ ] webhook تأیید پرداخت → تغییر وضعیت escrow به `HELD`
- [ ] `POST /transactions/:id/release` بعد از تأیید دو طرف → `RELEASED`
